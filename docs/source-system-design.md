# Source System Design

How the three ERP systems behave, what their extracts look like, and why each difference
matters. Phase 2 *creates* these differences; Phase 3 is the first place any of them is
removed.

Generated by `src/generation/erp.py`. Machine-readable conventions:
[`config/coa/erp_source_profile.csv`](../config/coa/erp_source_profile.csv).

---

## 1. Why the systems stay different

Northstar grew by acquisition and never migrated anyone. Three ERPs remain, and the
platform's whole justification is that reconciling them by hand takes four days a month.
If Phase 2 quietly normalised them — one date format, one sign convention, one account
shape — Phase 3 would have nothing to do and the engagement would be a demonstration of
software that solves a problem nobody has.

So the extracts are deliberately awkward, in the specific ways real extracts are awkward.

| | **Aurora** | **Sable** | **Kestrel** |
|---|---|---|---|
| Archetype | Modern cloud ERP | Project / job-cost ERP | Legacy European ERP |
| Entities | 5 (`NIG-100`, `110`, `200`, `210`, `500`) | 3 (`NIG-300`, `310`, `400`) | 4 (`NIG-220`, `320`, `410`, `510`) |
| Journal lines | 526,068 | 371,224 | 185,116 |
| Account key | 4-digit numeric | 5-digit numeric | **8-character zero-padded text** |
| Amount columns | one signed `AMOUNT` | one `AMOUNT` at natural sign | **`SOLL` / `HABEN`, both positive** |
| Delimiter | comma | comma | **semicolon** |
| Encoding | UTF-8 | UTF-8 | **Windows-1252** |
| Decimals | `1234.56` | `1,234.56` | **`1.234,56`** |
| Dates | `2025-03-14` | `03/14/2025` | **`14.03.2025`** |
| Periods | 1–12 | 1–12 | **1–12 plus 13** |
| Extra currency column | system USD (stale) | none | **legacy group EUR** |
| File naming | `AURORA_GL_<company>_<YYYYMM>.csv` | `SABLE_LEDGERTRANS_<company>_<YYYYMM>.csv` | `KESTREL_BSEG_<company>_<YYYYMM>.csv` |

507 extract files, one per entity per period, in `data/raw/{aurora,sable,kestrel}/`.

## 2. Sign conventions — the three-way problem

This is the difference most likely to cause a silent, total inversion of an entity's income
statement, so it is worth stating precisely. All three rules are declared in
`erp_source_profile.csv` and all three are exercised by control `P2-SRC-03`, which parses
the raw files back and re-derives a signed amount.

**Aurora — one signed amount, credits negative.**
```
AMOUNT = -158,204.11        →  signed = -158,204.11
signed_amount = AMOUNT
```
The modern case. Nothing to do.

**Sable — natural sign per account, direction from the chart.**
```
MAINACCOUNT = 40100 (revenue, normal balance C)
AMOUNT      = 158,204.11    →  signed = -158,204.11
signed_amount = AMOUNT * (1 if normal_balance = 'D' else -1)
```
A reader who does not know each account's normal balance **cannot** recover the sign. The
chart is not optional metadata here; it is part of the data. Note also the thousands
separator, which means the field must be parsed, not cast.

**Kestrel — separate debit and credit columns.**
```
SOLL = "158.204,11"  HABEN = ""    →  signed = +158,204.11
SOLL = ""  HABEN = "158.204,11"    →  signed = -158,204.11
signed_amount = parse_de(SOLL) - parse_de(HABEN)
```
Classic European ledger shape. A posting key (`BSCHL` 40/50) is carried alongside for
traceability but is deliberately *not* the source of truth for direction — using it instead
of the amount columns is a common shortcut that breaks on reversal documents.

## 3. Aurora

```
SUBSIDIARY,PERIOD,TRANDATE,JOURNAL_ID,LINE_ID,ACCOUNT,ACCOUNT_NAME,DEPARTMENT,CLASS,
LOCATION,MEMO,DOCUMENT_NUMBER,DOCUMENT_TYPE,CURRENCY,AMOUNT,AMOUNT_USD_SYSTEM,
SUBSIDIARY_PARTNER,CUSTOMER,ITEM,LINE_ATTRIBUTES
```

- **Dimensions**: `DEPARTMENT` (`DEPT-D100`), `CLASS` (repurposed to carry the event type,
  as cloud ERPs often are), `LOCATION`.
- **Intercompany partner** in `SUBSIDIARY_PARTNER`, on both legs of every intercompany entry.
- **`AMOUNT_USD_SYSTEM` is a trap.** Aurora translates using its own rate table, which runs
  a month behind the treasury rate file. It is populated so that the extract looks real,
  and control `CTL-FX-06` requires that Phase 3 ignore it. Translating an already-translated
  amount produces a triangulated rate error that is very hard to find later.
- **The material mapping problem lives here.** Account `6100` *Salaries and Wages* carries
  direct production labour, indirect labour and SG&A payroll alike. Only `DEPARTMENT`
  determines whether a dollar sits above or below gross margin. Fault fixture **F08** shows
  what happens when that attribute is wrong: every balancing control still passes, and only
  gross margin moves.

## 4. Sable

```
COMPANY,FISCALYEAR,FISCALPERIOD,POSTINGDATE,JOURNALID,LINENUM,MAINACCOUNT,ACCOUNTNAME,
NORMALBALANCE,DIMENSIONSTRING,DESCRIPTION,DOCUMENTNUM,DOCUMENTTYPE,TRANSACTIONTYPE,
CURRENCYCODE,AMOUNT,CUSTOMERID,ITEMID,LINEATTRIBUTES
```

- **Company codes are alphanumeric** (`CAS-US`, `CAS-CA`, `VEC-US`), not entity codes. The
  entity has to be resolved through the entity master.
- **Dimensions are packed into one pipe-delimited string**:
  `DIMENSIONSTRING = 300|D200|NOPROJ|NONE` → business unit, department, project,
  intercompany partner. It must be split before anything can be joined to it.
- **`NORMALBALANCE` is carried on the line** as a convenience, but the chart remains
  authoritative — a real extract cannot be trusted to be self-describing.
- **Job-cost structure**: because Sable was built for project work, direct labour *is*
  separable at account level (`50100 Job Cost - Labor`), unlike Aurora and Kestrel. The
  three systems are not uniformly bad in the same places.
- **Thin accrual structure**: Sable has no accrued professional fees, warranty or
  restructuring accounts, and no finished goods. Those postings substitute into
  `22900 Other Accruals` and `13200 Job WIP`, recorded in the expected-mapping manifest as
  `substituted_because_unavailable = TRUE`.

## 5. Kestrel

```
BUKRS;GJAHR;MONAT;BUDAT;BELNR;BUZEI;HKONT;TXT50;SAKNR_BEZ;KOSTL;PRCTR;SEGMENT;VBUND;
BSCHL;WAERS;SOLL;HABEN;DMBTR_KONZERN_EUR;KUNNR;MATNR;ZUONR
```

Every field name is the German original, because the system is. Six deliberate hazards:

1. **Windows-1252 encoding.** Reading it as UTF-8 corrupts the German account names in
   `SAKNR_BEZ` (*Verbindlichkeiten aus L+L*, *Loehne und Gehaelter*).
2. **Semicolon delimiter**, because the comma is the decimal separator.
3. **`1.234,56` amounts.** Parsed naively as US-locale, `1.234,56` becomes `1.23` — a
   thousand-fold understatement that still looks like a number. Fault fixture **F06**.
4. **Zero-padded 8-character account keys** (`00091000`). Read as an integer, `00091000`
   becomes `91000` and joins to nothing. `P2-FMT-02` asserts the leading zeros survive.
5. **Special periods 13 to 16.** Post-close adjustments are filed under `MONAT` values
   above 12, not December. Treating them as extra months breaks every monthly comparison;
   treating December as missing raises a false period-completeness failure. All four map to
   December with an adjustment flag. See §5.1.
6. **`DMBTR_KONZERN_EUR`** is a legacy group-currency column inherited from Halden Valve's
   pre-acquisition parent. It is a EUR translation at Kestrel's own rates and must never be
   used (`CTL-FX-06`).

### 5.1 The four special periods

A German ledger does not close once. The statutory close happens first, the auditor's
findings arrive months later, the tax position settles only on filing, and the group
reporting alignment is booked separately again. Each lands in its own special period, and
each is populated by a rule that reflects when that kind of adjustment actually arises. The
definitions are configuration, not code: `config/coa/kestrel_special_periods.csv` carries the
purpose, who posts it, its timing, its entry nature and its population rule.

| Period | German | Purpose | Posted by | Timing | Population |
|---|---|---|---|---|---|
| **13** | *Abschlussbuchungen* | Statutory close: the income statement is closed into `00071500 Jahresergebnis` | Local finance | Within 15 working days of the year end | **Every** Kestrel entity, every closed year — 11 company-years |
| **14** | *Prueferbuchungen* | Audit reclassifications: misclassified accruals, professional fees against the wrong category, receivables presented gross | External auditor via local finance | Two to four months after the year end | Only where a finding actually arose — 5 of 11 company-years |
| **15** | *Steuerbuchungen* | Tax true-up on filing: reallocation between corporate income tax and trade tax, and the same split on the balance sheet | Local tax adviser | Six to nine months after the year end, on filing | Every entity for every **filed** year — 11 company-years |
| **16** | *Konzernanpassungen* | Local GAAP to group policy: HGB-measured warranty and restructuring provisions reclassified to the group's categories | Group financial control with local finance | Alongside the group reporting submission | Only where the provision exceeds group financial control's reporting threshold — 4 of 11 company-years |

Three properties are worth stating because they are easy to get wrong and are tested:

- **Periods 14 to 16 are reclassifications, not restatements.** Each entry moves an amount
  within a single anchored caption, so the year's reported result and every anchored subtotal
  are unchanged (`P2-FMT-09`). That is correct rather than convenient: the group's reported
  result *is* the approved anchor, so the generated ledger is the audited outturn. Modelling a
  pre-audit ledger that differed would require an unaudited scenario, which is out of scope.
- **Unfiled years carry nothing.** FY2026 is neither audited nor filed at the reporting date,
  so it has no period 14 and no period 15 (`P2-FMT-08`).
- **Conditional periods must be conditional.** Period 13 is universal; 14 and 16 must be
  present but not universal, or the population rule is not modelling anything (`P2-FMT-07`).
  An audit finding at every entity every year would be as unrealistic as none at all.

Period 16 deliberately excludes the operating lease right-of-use asset. The Kestrel entities
do not recognise it locally at all, so there is nothing in their ledgers to reclassify; Phase
3 raises it as a staging top-side entry instead (§9).

**Plus the accounting-presentation difference.** Kestrel entities report on the German
*Gesamtkostenverfahren*: `00081000 Bestandsveraenderung` (change in finished goods) and
`00081200 Aktivierte Eigenleistungen` (own work capitalised) sit **above the revenue line**.
Under the group's cost-of-sales presentation both belong in cost of sales, with a sign
reversal. Leaving them in revenue overstates both revenue and gross margin for three of the
twelve entities.

Kestrel also has no cost-of-sales detail at all — no freight, duty, consumables, equipment
hire or warranty accounts — because a nature-of-expense chart classifies by *what was
bought*, not *why*. Those postings substitute into `00090000 Materialaufwand` and
`00090400 Aufwendungen fuer bezogene Leistungen`.

| | Aurora | Sable | Kestrel |
|---|---|---|---|
| Source accounts | 146 | 131 | 115 |
| Shared account codes with either other system | 0 | 0 | 0 |
| Group accounts posted to | 112 | 97 | 104 |
| Conditional-split inversions recorded | 27 | 28 | 47 |
| Substituted accounts (the ERP has no equivalent) | 1 | 8 | 14 |

`P2-FMT-03` asserts the three charts share no account code — a guard against a future
change quietly converging them.

## 7. The expected-mapping manifest

Phase 2 must choose a source account for every posting, which means inverting the approved
Phase 1 mapping. That inversion is recorded rather than hidden, in
[`config/generation/expected_mapping_manifest.csv`](../config/generation/expected_mapping_manifest.csv):

| Column | Meaning |
|---|---|
| `erp_system`, `source_account` | what the extract contains |
| `mapping_type` | `DIRECT`, `MERGE`, `SPLIT`, `DERIVED` |
| `requested_group_account` | what the generator wanted to post |
| `expected_group_account` | what Phase 3's mapping engine must produce |
| `required_line_attributes` | the attributes a conditional split has to read, e.g. `dept_function=PRODUCTION` |
| `substituted_because_unavailable` | `TRUE` where the ERP has no equivalent account |

The manifest has 313 rows. Every generated journal line also carries its own
`expected_group_account` in
`data/reference/journal_lines.parquet`. **Phase 3 is graded against that column**: for
1,082,408 lines, the mapping engine must reproduce it exactly. Phase 2 performs no
mapping — it only records what the answer is.

## 8. What each extract does *not* contain

Deliberate, and load-bearing for later phases:

- **No goodwill, acquired intangibles or their deferred tax.** These are recognised on
  consolidation (layer 3), so no entity's own ledger carries them.
- **No consolidated or translated figures.** Every extract is in the entity's own
  functional currency, at its own trial balance.
- **No group chart of accounts.** Only source accounts.
- **No elimination entities.** `ELIM-IC`, `ELIM-CON` and `ELIM-MGT` are virtual and never
  produce an extract; `P2-REF-02` asserts it.
- **No operating lease right-of-use assets in the Kestrel entities**, which do not
  recognise them locally. Phase 3 raises them as a staging top-side entry.
